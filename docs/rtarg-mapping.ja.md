# Reflexive Thematic Analysis Canvas と RTARG の対応表

**Reflexive Thematic Analysis Reporting Guidelines（RTARG：再帰的テーマ分析の報告ガイドライン）** の各項目について、Reflexive Thematic Analysis Canvas がどう対応しているかをまとめた表です。アプリが良い報告を支えている点、研究者が自分で書くべき点、まだガイドラインとぶつかっている点を示します。

> Braun, V., & Clarke, V. (2024). Supporting best practice in reflexive thematic analysis reporting in *Palliative Medicine*: A review of published research and introduction to the Reflexive Thematic Analysis Reporting Guidelines (RTARG). *Palliative Medicine, 38*(6), 608–616. https://doi.org/10.1177/02692163241234800 — RTARG は論文の補足資料（Supplemental Material）に収録されています。論文は CC BY 4.0 で公開されています。

この対応表についての注意:

* RTARG の各項目は**要約**です。報告の際は必ず原文を確認してください。項目番号はこの表で独自に振ったもので、原文では見出しの下に番号なしで並んでいます。
* RTARG は**チェックリストではなくガイドライン**です。すべての項目がすべての研究に当てはまるわけではなく、考えずに従っても報告の質は上がりません。このアプリについても同じことが言えます。アプリは再帰的テーマ分析を支えられますが、分析を再帰的にするのは研究者自身です。
* RTARG は項目ごとに**避けるべき慣行**も挙げています。アプリがその方向に誘導しかねない場合は、最後の列に書いています。

**区分：**

| 印 | 意味 |
|---|---|
| ✅ | 対応済み：アプリが行うか、そのための材料を作る |
| 🟡 | 一部対応、または間接的に対応 |
| ✍️ | 研究者の執筆や研究デザインの判断で、アプリの外の作業 |
| ⬜ | 未対応だが、アプリで支援できる |
| ⚠️ | 衝突：アプリが現在、RTARG が避けるよう求めることをしている |

## 序論（Introduction）

| # | RTARG の推奨（要約） | 区分 | アプリでの対応／今後すべきこと |
|---|---|---|---|
| 1 | 確かな背景と根拠を示す。「研究の空白を埋める」ではなく、既存研究との対話に加わる | ✍️ | — |
| 2 | 方法論的に一貫したリサーチクエスチョンを示す（仮説にしない） | 🟡 | 「プロジェクト設定 → リサーチクエスチョン」に書け、「分析の概要」に載る。書き方は研究者次第。 |
| 3 | 自分の視点を引き受ける：理論的前提（パラダイム・存在論・認識論）と、依拠する理論を書く | ✅ | 「プロジェクト設定 → 分析の立場・データの準備 → 理論的前提と依拠する理論」（任意）。「分析の概要」に載り、変更は変更前・変更後とともに記録される。 |
| 4 | その前提と一貫した書き方を全体で保つ（解釈の「正確さ」「信頼性」を語らない） | 🟡 | アプリ自身の文言は、正確さ・信頼性の言い回しを使わず、テーマは「見つかる」ではなく「生成する」もの。研究者の文章は研究者のもの。 |
| 5 | 前提・問い・データ生成・分析方法の方法論的な一貫性を示す | 🟡 | アプリは再帰的テーマ分析専用で、コードブックの方式も一致率もない。研究全体の一貫性は研究者が担う。 |
| 6 | 省察の実践を示す（立場、役割、省察ジャーナル） | ✅ | 省察ジャーナル（Ctrl/⌘+J でどこからでも書ける。種類に「研究者自身の社会的な立場（ポジショナリティ）」あり）、判断に添える任意の「理由」、テーマ構造のスナップショット、付録A。 |
| 7 | 一人称で書く | 🟡 | 分析の記述画面の説明で、一人称で書くよう勧めている（「テーマを作ったのは自分」）。文体は研究者が決める。 |

## 方法論（Methodology）

| # | RTARG の推奨（要約） | 区分 | アプリでの対応／今後すべきこと |
|---|---|---|---|
| 8 | 参加者・データの選び方を書く（「サンプル／サンプリング」という語は避ける） | ✍️ | アプリは「サンプル」という語を使っていない。 |
| 9 | 参加者・データの数と、その根拠を示す（例：information power。飽和は根拠にしない） | 🟡 | 「分析の概要」に文書数と参加者数（聞き手を除く）が載る。根拠は研究者が書く。アプリは「飽和」に一切触れない。 |
| 10 | 参加者の特性を、文脈と匿名性の兼ね合いを取って書く（まとめた形か、最小限の属性で） | ✅ | 表1は初期設定で参加者グループとしてまとめて示す（属性ごとに、値と該当人数。聞き手は除く）。該当者が1人だけの値はプレビューで指摘する（出力には含まない）。1人1行の表は、匿名性の注意を添えた明示的なオプションにした。 |
| 11 | 倫理審査・原則・同意を書く。匿名性を損なわない | ✍️ | データはブラウザの外に出ず、参加者には仮名のラベルを使える。報告は研究者が書く。 |
| 12 | データ生成の方法を選んだ理由を書く（トライアンギュレーションを理由にしない） | ✍️ | — |
| 13 | データ生成の道具（インタビューガイドなど）を説明し、できれば補足資料に入れる | ✍️ | — |
| 14 | 実施方法・場・期間・記録方法を書く（標準化されていないことを偏りとして扱わない） | ✍️ | — |
| 15 | 対話的なデータ生成を誰が行ったか、その人の立場や参加者との関係を書く | 🟡 | 聞き手は聞き手としてタグ付けできる。立場の開示はジャーナル（研究者自身の社会的な立場（ポジショナリティ））と論文で書く。 |
| 16 | データの規模を書く（例：インタビューや文章の長さの範囲と平均） | ✅ | 「分析の概要」に、文書と自由記述の回答それぞれの長さの範囲と平均を載せる（文字数。空白で区切る言語では語数も）。注記で、長さはデータの記述であり質の指標ではないと示す。 |
| 17 | データの準備を書く：文字起こし、修正、個人を特定できる情報の削除、仮名化 | ✅ | 「プロジェクト設定 → データの準備」（任意）。「分析の概要」に載る。取り込んだ文章はそのまま保持され、文字コードも記録される。 |
| 18 | 再帰的テーマ分析を使う理由を書く。コードブックなど他の方法と組み合わせるなら、その正当性を示す | 🟡 | アプリは再帰的テーマ分析専用で、コードブックはない。コード一覧は分析の記録であり、初期設定では出力しない。理由は研究者が書く。 |
| 19 | 再帰的テーマ分析での分析の志向を書く（帰納的⇔演繹的、意味的⇔潜在的） | ✅ | 「プロジェクト設定」で、それぞれ5段階から選べる（任意）。「分析の概要」に載り、変更は記録される。 |
| 20 | 6つのフェーズの一般的な説明ではなく、この研究での具体的な分析過程を書く（補足資料を活用） | ✅ | 監査証跡、ジャーナル、判断の理由、「その時点の構造」のスナップショットが、実際の過程を記録する。付録Aとして補足資料に出力できる。アプリが6つのフェーズの一般的な説明文を出力することはない。 |
| 21 | 複数人で分析したなら、役割、共同でのコーディングの進め方、意見の違いの扱いを書く（一致率や合意によるコーディングはしない） | 🟡 | すべての操作とジャーナルに分析者の名前が記録される。ジャーナルの「指導教員・チームとの打ち合わせ」は、この項目のための見本（参加者、読みが分かれたところ、それぞれの根拠、どう扱ったか、何が変わったか）から書き始められる。一致率やプロジェクトの統合は、意図して設けていない。チームでの進め方は README に記載。 |
| 22 | 研究者が能動的に作ったことが伝わる言葉を使う（テーマは「生成した」「展開した」。「浮かび上がった」「見つかった」「特定した」は避ける） | ✅ | アプリの文言は英語・日本語ともこれに従っている（例：「初期テーマの生成」「候補テーマ」）。 |

## 分析（Analysis）

RTARG は、見出しを *Results*（結果）や *Findings*（知見）ではなく **Analysis（分析）** にするよう勧めています。アプリが出力する原稿の見出しも「分析」／“Analysis” です。

| # | RTARG の推奨（要約） | 区分 | アプリでの対応／今後すべきこと |
|---|---|---|---|
| 23 | テーマやテーマ構造の全体像を示す（一覧・図・表） | ✅ | 「テーマ → 関係図」：テーマ、サブテーマ、名前を付けたテーマ間の関係を示す図。.svg で保存でき、Word の原稿に図1として入る。「テーマと抜粋」の表と記述の見出しでも構造が分かる。 |
| 24 | テーマを、核となる意味（中心概念）でまとまった共有された意味として捉える（話題の要約にしない） | ✅ | フェーズ5の定義欄でテーマの核となる意味（中心概念）を尋ねる。テーマ画面が空のときの説明文で、テーマは話題の要約ではなく共有された意味のパターンだと伝える。 |
| 25 | テーマの名前は、その本質や物語を表すものにする（一語の話題名にしない） | 🟡 | 「見直し済み」「定義済み」のテーマで、名前が短く話題名のように見える場合、名前で物語を伝えられる（短い引用も使える）という穏やかなヒントを出す。名前の変更は記録される。 |
| 26 | テーマを深く書く：多面的で、データと分析の記述の両方を含む。テーマ数を多くしすぎない | 🟡 | テーマごとに記述欄がある。テーマが8個を超えると、まとめるか保留にすることを提案する。 |
| 27 | サブテーマは慎重に使い、構造を細切れにしない | 🟡 | サブテーマは1階層まで。サブテーマが4個以上のテーマには穏やかなヒントを出す。 |
| 28 | 分析の記述で、データの意味と重要性を説明する（出現頻度をテーマの根拠にしない。データに「語らせる」だけにしない） | ✅ | フェーズ6は分析の記述の画面から始まる。出現頻度の数は初期設定で隠し、選ばない限り出力しない。 |
| 29 | 分析の記述と、データ全体から選んだ抜粋のバランスを取る | ✅ | テーマの抜粋を記述欄の横に並べ、カーソルの位置に挿入できる。表の代表抜粋は、研究者が★を付けた代表抜粋だけ。どの抜粋で示すかは分析上の判断なので、自動では補わない。 |
| 30 | 記述と抜粋を一致させ、別の読み方も検討する | ✍️ | どの抜粋も元の文書の該当箇所に戻れるので、文脈の中で読み直すのに役立つ。全文書の全文検索で、テーマに収まりきらない語りを探せる。抜粋の絞り込みで、あるコードの抜粋をグループごとに読み比べられる（読むためだけの表示で、数や出力は変わらない）。 |
| 31 | 既存の研究や理論を、分析の記述の中に織り込む（「結果」と「考察」を分けない） | 🟡 | 分析の記述画面の説明で、研究や理論を別の考察に回さず各テーマの記述に織り込むよう勧めている。書くのは研究者。 |

## まとめ

* **対応済み（✅）：**
  * 立場：理論的前提、分析の志向、データの準備（3, 17, 19）
  * データ：文書と回答の長さ（16）、匿名性を守るためグループとしてまとめた参加者の特性（10）
  * 過程：省察の実践と分析過程の記録（6, 20, 34, 36）、一貫した言葉づかい（22）
  * 分析：テーマの捉え方（24）、テーマの関係図（23）、出現頻度に頼らない分析の記述（28, 29）、テーマ間のつながりと全体のまとめ（32）
* **衝突：** なし。表1は初期設定でグループとしてまとめるようにした（10）。
* **間接的に対応（🟡）：** テーマ名、サブテーマ、テーマの数、一人称、理論の織り込みについての、作業を止めない穏やかなヒント（7, 25, 26, 27, 31）。アプリは促せるが、最終的には執筆上の判断として残る。
* **研究者の仕事（✍️）：** 研究デザイン、倫理、データの生成、考察。アプリは分析を記録し整理しますが、方法論の記述を代わりに書くことはしません。
